# codex-devteam

PM、TL（Tech Lead）、実装担当、Codex監査、Claude監査を独立セッションで運用するAI開発フローです。PMが案件の目的・現在地・リスクから必要な作業を決め、実装担当が既存パターンに沿って実装・検証・修正を行います。

`docs/flow/`の現行資料と実コード・検証証拠で進めます。flowctlによる工程管理・開始承認・状態同期は行いません。役割・工程成果物の所有権・危険操作の安全ガードだけを補助に使います。

## 役割を開始する

新しいセッションではai-devteamは無効です。役割を明示して開始した後は、同じセッションで役割を継続します。途中の質問や「進めて」で呼出し名を再指定する必要はありません。説明や引用に呼出し名が現れただけでは開始しません。

| 役割 | Codex | Claude |
| --- | --- | --- |
| PM | `$pm` | `/pm` |
| Tech Lead | `$tl` | `/tl` |
| 実装担当 | `$implementer` | `/implementer` |
| 独立監査 | `$auditor` | `/auditor` |

この配布物はCodexの4役とClaude監査を含みます。Claudeを主担当にする場合はclaude-devteam側の配布物を使います。

各役割はユーザーが独立セッションで開始します。PM・実装担当は同じ機能内で継続利用できます。別の正式役割をサブエージェントで代行しません。現役割内の調査や検証では利用できます。

ただしオーナーが同じtaskの監査役へ「あなたが対応する」「あなたが修正する」「あなたが実装する」「PM兼実装担当として進める」と明示した場合、その会話は実装、またはPM兼実装のowner-directedへ切り替わります。新規セッションやコピペは不要です。元の監査は独立監査件数に含めず、再監査の要否・件数は残るリスクを示したうえでオーナーが決めます。

## 基本フロー

```text
PM: 壁打ち、既存決定の引継ぎ、仕様・指示書
  → 新しい上流判断が必要な場合だけTL
実装担当: 既存調査 → 実装 → 検証 → 修正
  → テストだけで高リスク境界を証明できない場合だけ内部Evaluator
  → report / summary / loop-stateをPMへ提出
PM: 仕様・実差分・検証を裏取り、正式文書を更新
オーナー: コミット
PM: 確定した差分で監査依頼を作成
Codex監査・Claude監査: 独立した確認
PM: 結果整理。残件は実装担当へ戻す
オーナー: リリース・クローズ判断
```

監査は基本2件です。オーナーが1件または再監査なしを明示した場合は、残るリスクと省略理由を記録して従います。テスト成功や内部Evaluatorだけで完了とせず、PM確認と必要な独立監査を行います。既にコミット済みの作業は、その差分と証拠を確認して利用します。

## PMは判断を先に出す

初めて扱う機能・task・既存案件では、PMは急いで結論を出しません。目的・完了条件・オーナー決定、現在地、現行指示、最新の提出／監査整理、Git差分、必要なコード入口を照合し、全体像を把握してから最初の判断を出します。資料量が多い場合は、確認済み範囲と残りを途中共有します。

初回把握後の同じ機能の相談では、目安3分で`判断`、`根拠`、`未確認`、`次の1手`を返します。`docs/flow`の現在地、最新の指示・summary・report・監査整理を証拠索引として使い、整合している限り全repo・全履歴・全テストを読み直しません。ユーザーが目的、対象環境、実装不要、優先順位を訂正したら、PMは直前の調査を止めて新しい判断を先に返します。

テストは影響範囲で選びます。局所変更は直接テストと必要な静的検査、複数領域・外部契約は関連統合テストと必要なbuild、認証・migration・共有基盤・依存更新・広域リファクタ・影響不明だけは広域回帰を検討します。同じ版のCI証拠をPMがローカルで反復することはありません。

既存CLI・Workflow・runbookの実行確認では、既存の正式手順だけを使います。PMは一時診断スクリプト、隠しファイル、環境変数の手組み、credential探索、ローカル代替経路を作りません。既存の診断で原因を特定できなければ、その診断性不足を報告し、診断機能の追加は別の実装判断にします。

## 文書資産の読み方・残し方

機能ごとの`tasks.md`冒頭に、PMが短い「現在地」を維持します。既存の同等の索引があればそれを使います。

| 現在地に残すもの | 目的 |
| --- | --- |
| 目的と完了条件、オーナーの決定 | セッション途中でも目標を維持する |
| 現在repo/task、作業状況、確認日時 | 途中参加で現在地を把握する |
| 最新指示・報告・監査整理・関連決定のリンク | 根拠へ直接進む |
| 未解決事項と次の担当・作業 | 次の依頼を具体化する |
| 確認済みGit境界、並行差分、関連repo | 古い証拠と現在差分を混同しない |

ユーザーが指定した資料と現在地を起点に、必要な仕様・TL決定・監査・報告を参照します。過去資料は判断の根拠として保存し、全資料・全Git履歴を毎回読み直しません。名前や更新日時だけで最新・完了と断定せず、参照関係と対象差分を確認します。

主な配置は次のとおりです。既存名の指示書や監査はリンクで再利用できます。

```text
docs/flow/<feature>/
  spec.md                       確定仕様
  tasks.md                      現在地とタスク一覧
  scope-baseline.md             必要な場合の承認範囲メモ
  tech-lead/                    上流の相談と決定
  task-NN/
    instruction.md              現行指示の入口
    pre-summary.md              既存調査
    loop-state.md               実装・検証・修正の記録
    report.md / summary.md      実装提出
    implementation-review.md    PM確認
    audit-request*.md           PMが指定する今回の監査依頼
    audit-codex*.md              Codex監査
    audit-claude*.md             Claude監査
    audit-triage.md              PMの監査整理
```

工程資料と規約ファイルはローカル資産としてgitignoreします。機能完了後も削除しません。恒久的に必要な仕様はPMが正式文書へ反映してコミット対象にします。README・ガイド・設計書等の正式文書を実装担当に編集させません。

実装中に追加・変更するコードコメントの文末には「。」を付けません。JavaScript・TypeScript等の関数説明は複数行JSDocとし、必要なら引数の意味・制約を`@param`へ記します。定数・型の説明と関数内の補足は`//`を使います。ドキュメント・工程資料の句点は使用できます。表記統一だけの既存コメント一括変更は行いません。

マイグレーションは既存ツール・導入済みCLIによる生成を基本とします。Prismaの`migrate dev`は適用も伴い、`--create-only`でも開発DB・shadow DBを使用するため、隔離・破棄可能な環境で扱います。データ移行等の未適用SQL補正や、手書きSQLが正規方式の案件は許容します。適用済み履歴は編集せず、新しいマイグレーションで修正します。

## 状況に合う工程を使う

- 壁打ち・キャッチアップでは、必要な資料を読んで現在地や選択肢を返します。工程初期化や全テストを定例追加しません。
- 既存要件の不具合・監査是正では、最新指摘と現在差分から残件を指示書にまとめます。既存の設計判断を再利用します。
- 新規開発では、期待結果、対象外、責務、リスク、検証方法を具体化します。
- 認可・テナント分離・秘密情報・不可逆処理等の方式が新たに未決ならTLへ相談します。既存設計の重大な欠陥も対象です。DBや外部APIを触るという名称だけではTL承認を追加しません。
- ユーザーの質問・候補案は自動採用しません。採用済み目的に不可欠な範囲内の不足は同じtaskへ含め、新しい成果・責務・リスクは差分を示して判断します。
- 「急いで」は監査・検証・リリース条件を緩和する許可ではありません。

## 指示書と安全ガード

文書運用ではPMの指示書に、目的、対象外、受け入れ条件、検証方法、変更対象の責務、既存パターンの参照先を記します。見出し・表・globの定型は要求しません。

実装担当はrole-start時に指示書へ関連付けられ、正式文書・秘密情報・Git管理領域の編集を拒否されます。実装前確認後はループへ入り、提出と監査への受け渡しは文書で行います。scope-lock、init、preflight-complete、submit等の工程操作は廃止しています。

旧policy・state・scope-lockが残るtaskも同じ文書運用です。履歴は削除・変更せず、開始・成果物保存の条件にしません。初期化、スコープ再固定、提出・監査の状態同期、移行用taskの複製は不要です。実行中の指示は担当を止めて差分を伝え、同じ担当が読み直します。

監査担当はPM指定の実在する依頼書を読み、実コード・テスト・仕様を独立確認します。ファイル名を固定名へ揃える必要はありません。SHAは確認した版の証拠としてAIが取得・記録します。現在HEADが先へ進んでも、指定された過去コミットをその版のまま監査できます。別版の検証結果や対象不明を合格扱いにはしません。オーナーが監査役へ同じtaskの是正を明示した場合は、同じ会話で実装またはPM兼実装へ切り替えます。

廃止された工程コマンドは互換案内だけを表示し、変更・承認・停止解除は行いません。オーナーの停止指示、未解決の仕様・安全条件・監査指摘は引き継ぎます。

## コマンドの担当

| 担当 | 操作 |
| --- | --- |
| 各AI役割 | role-startを初回に実行。現在地や対象が既知なら同じ登録を反復しない |
| PM | 必要資料・指示・提出確認・監査整理。工程コマンドは不要 |
| 実装担当 | 実装ループとPM提出。工程コマンドは不要 |
| オーナー | Git、リリース、最終判断。実際の破壊・共有環境・外部状態変更だけを個別に判断 |
| フック | 明示開始した役割の操作を自動検査。通常セッションは対象外 |

所在が不明なときの読取り補助です。指定ディレクトリと直下のプロジェクトのdocs/flowを列挙し、現在taskは推測しません。

```sh
~/.ai-devteam/bin/flowctl status \
  --project-root <project-or-workspace>
```

対象taskが既知なら次を使えます。statusはファイルを書き換えません。

```sh
~/.ai-devteam/bin/flowctl status \
  --task-dir docs/flow/<feature>/task-01
```

AIがオーナーへコマンドを提示する必要があるのは、Git、リリース、実credential・本番・共有環境、または実際の外部状態変更だけです。提示時はshコードブロック、実際のバックスラッシュ継続、1オプション1行で示し、パス途中を改行しません。

## 安全制御と計測

役割外の編集、秘密情報パス、Git変更、実credential・本番・共有DB、破壊操作、実際の外部状態変更を制限します。依存変更・install、読取り専用のネットワーク取得、隔離・破棄可能なDBでのmigration／DB検証にはflowctl許可を使いません。

フックは対応ツールの呼出しを検査する補助制御であり、子プロセス内部まで隔離するOS sandboxではありません。必要なら同梱のCodex権限プロファイルを併用します。

metricsは旧工程の参考履歴です。現在の文書進行の所要時間・差し戻し率・初回監査合格率は自動集計しません。役割の開始・終了時刻は実作業時間とは異なり、未計測を0秒や改善済みと報告しません。

内部Evaluatorは高リスク時の補助確認です。形式検査だけで別コンテキストの実体や品質を証明しません。文書運用の監査合格・次工程は、PMと独立監査が証拠に基づいて判断します。

## セットアップ

配布元で実行します。

```sh
sh scripts/install.sh
```

テスト後に役割Skill、flowctl、Codex/Claudeフック、Codex権限プロファイルを配備します。プロジェクトへAGENTS.mdとCLAUDE.mdを配置します。旧claude/settings.jsonのGit deny雛形はコピーしません。

すでにフックが導入済みなら、規約とSkillを既存セッションで読み直して継続できます。フックを初めて導入・設定変更した場合は、クライアントに読み込ませるためセッションを再開します。

```sh
~/.ai-devteam/bin/flowctl diagnose \
  --project-root <project>
```

旧Claude静的Git権限が検出された場合だけ、オーナーがremove-legacy-claude-guardsを使えます。既知の旧権限だけをバックアップして除去し、その他の設定を保持します。

## 検証

```sh
python3 -B -m unittest discover -s tests
```

回帰テストは役割継続、監査からのオーナー指示による転用、旧stateに依存しない監査、秘密情報・権限境界、読取り専用の所在確認を検証します。PMの判断品質はtests/pm-scenarios.mdの運用シナリオでも確認します。単体テストの合格だけで実案件の速度や判断精度を保証しません。
