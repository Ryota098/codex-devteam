# 制限付き実装ループ

実装前サマリが承認された後、または軽量パスで省略が明示された後に、このループを実行する。

## 反復手順

1. 未達の受け入れ条件から、最小の実装単位を1つ選ぶ。
2. 既存パターンと承認済み範囲に沿って実装し、必要なテストを同時に追加・更新する。
3. まず変更に直接関係するテストを実行し、失敗原因を確認して修正する。
4. 関連テストが通ったら、プロジェクトで必須のテスト・lint・型チェック・format・buildを必要な範囲で実行する。
5. `git diff` と `git status` を読み、仕様逸脱、範囲外変更、意図しない生成物、秘密情報、既存パターンとの不整合がないか確認する。
6. 成功条件が未達で、安全に修正できる場合だけ次の反復へ進む。

## 成功条件

- 指示書とspec.mdの受け入れ条件を満たしている。
- 必要な正常系・失敗系・境界値・副作用のテストがある。
- 指定された検証がすべて成功している。
- 差分が承認済み範囲に収まり、既存規約・参照パターンと整合している。
- 未解決のセキュリティ懸念、既知の重大な不具合、無断のリファクタがない。

成功は「PMへ提出可能」を意味し、監査合格や機能クローズを意味しない。

## 上限と停止条件

- 指示書に別指定がなければ、実装と検証の反復は最大5回とする。
- 同じ原因の失敗が3回続く、または変更しても進展がない場合は停止する。
- 仕様・指示書・既存実装が矛盾している、変更範囲の拡大が必要、受け入れ条件を検証できない場合は停止する。
- サービス境界・アーキテクチャ・認証認可・秘密情報・個人情報・不可逆なデータ変更など、上流判断が必要になった場合は停止する。
- 破壊的操作、本番環境、共有DB、実credential、未承認の外部送信が必要な場合は実行せず停止する。
- 秘密情報の露出、権限逸脱、個人情報漏えいの疑いを見つけた場合は、値を表示・転記せず直ちに停止する。

停止時は推測で作業を続けず、試した内容、最後の安全な状態、失敗の根拠、必要な判断を私へ報告する。別役割を自分で起動しない。上流判断が必要でもTLへ直接渡さず、PMの独立セッションへ問題を戻すための貼り付け用プロンプトを提示する。

## 禁止事項

- テストの削除、skip化、アサーション弱体化、検証設定の緩和によって成功扱いにしない。
- 受け入れ条件、公開契約、エラー挙動を無断で変更しない。
- 指示範囲外の整理、命名変更、依存更新、リファクタを混ぜない。
- ループの途中でgit変更操作やコミット依頼を行わない。
- 環境変数や設定全体を一括表示せず、秘密情報をログや成果物へ残さない。

現在の実装担当業務内ではサブエージェントを使ってよいが、親セッションが全変更と検証結果を確認する。サブエージェントにPM・TL・監査を代行させず、その出力を独立した役割の成果物として扱わない。
