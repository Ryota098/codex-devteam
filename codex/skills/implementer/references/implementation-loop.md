# 制限付き実装ループ

PMの指示書と既存調査を確認した後、このループを実行する。機械管理taskでは`flowctl status`の`implementation`も確認する。既存調査とpre-summary.mdは同じセッションで行い、実装前Evaluatorやオーナー開始承認を挟まない。

## 反復手順

1. 未達の受け入れ条件から、最小の実装単位を1つ選ぶ。
2. 既存パターンと承認済み範囲に沿って実装し、必要なテストを同時に追加・更新する。認証・認可、入力検証、ログマスキングに関係する変更では、許可・拒否・不正入力・秘匿化を検証する。
3. まず変更に直接関係する最小の構文・型検査とテストを実行し、失敗原因を確認して修正する。複数言語・構文が混在する箇所は編集直後に検査する。
4. 関連テストが通ったら、プロジェクトで必須のテスト・lint・型チェック・format・buildと、設定済みの依存関係検査・秘密情報検査・静的解析を必要な範囲で実行する。必要な検査がCIにない場合、新規導入が指示範囲内なら追加し、範囲外なら勝手に追加せず提案と残リスクを記録する。
5. `git diff` と `git status` を読み、仕様逸脱、範囲外変更、意図しない生成物、秘密情報、既存パターンとの不整合がないか確認する。
6. Builderとして全受け入れ条件を満たす候補ができたら、高リスクまたはpolicyで必須の場合だけ、ユーザーの追加指示を待たず[internal-evaluator.md](internal-evaluator.md)を読み、別コンテキストの内部検証へ進む。低・標準リスクでは一律に起動せず、Builder検証、PM裏取り、独立監査を使い、省略根拠を記録する。
7. 内部検証が「修正必要」なら、根拠を確認して承認済み範囲内だけを修正し、関連テストからやり直す。「判定不能」なら不足情報を解消できる場合だけ再実行し、仕様判断が必要なら停止する。
8. 内部検証が「合格」になり、その後に実装・テストを変更していない場合、または省略条件を満たす場合だけ成功とする。合格後に差分を変えた場合は内部検証を再実行する。

各反復の受け入れ条件、検証結果、内部検証の判定、修正内容は `docs/flow/<機能名>/task-NN/loop-state.md` に記録する。内部検証については、実施方式を「別コンテキストのサブエージェント」と明記し、実行回数、ツールが返す場合は識別子、対象差分、判定、修正票、対応結果、合格後の差分変更有無を残す。秘密情報・個人情報や大量の生ログは記録しない。

実装中の発見は次のように分類する。文書運用ではloop-stateとPMへの引継ぎへ記録する。以下のflowctlコマンドは機械管理taskで該当する場合だけ使い、質問や軽微な修正ごとの定例操作にしない。

- 元の外部成果がその変更なしでは成立せず、固定済み変更パス・リスク領域内で、新しい利用者成果・責務を増やさない不足: `flowctl feedback --kind correction`へ根拠を記録し、同じ反復へ含める。必要最小限の内部処理、エラー処理、直接テスト、後方互換な最小クライアント拡張が該当し得る
- 質問・壁打ち・候補案だけで変更承認を伴わないもの: `--kind question`で記録し、回答してもコードへ自動反映しない
- 固定範囲は増えないが、既存方針だけでは解けない上流の技術・設計・セキュリティ判断: `--kind tl-review`で停止し、PMの`tl-request`と独立TL判断を待つ
- 新しい外部成果、利用者挙動、不可逆境界、固定glob、サービス責務、またはセキュリティ・課金・外部送信等のリスク領域を増やすもの: `--kind scope-change`で停止し、PMの差分提示、オーナーによるscope-baseline.md再固定、PMの`instruction-ready`を待って直接再開する
- flowctl・フック・検査器・互換性による停止で、外部成果、固定範囲、候補差分が変わらないもの: `--kind tooling-blocker`で停止する。スコープ基準や指示書を変更せず、ツール問題が解消した後に同じ実装担当セッションで`flowctl resume --task-dir <task-dir>`を実行する。resumeが候補差分digestと固定範囲を再検証するため、オーナー再固定・開始承認は不要

「あると良い」、将来用、関連しているだけの整理は必要な不足ではない。元の受け入れ条件が成立しない一次根拠を示せなければ実装せず、提案へ分ける。正式ドキュメントの更新必要性だけなら実装を広げず、report.mdでPMへ渡す。

オーナー・PM・監査からの是正は、指摘された挙動・ファイル・責務だけを新しい反復の変更予算とする。同種箇所への一律展開、周辺整理、コメント追加、命名変更は別の不具合を直すために不可欠でない限り混ぜない。

## マイグレーション

- 既存の移行方式、固定されたツールバージョン、package script、schemaと移行履歴の配置を確認する。生成可能なスキーマ変更は既存CLIで生成し、手動の日時ディレクトリ・SQL作成を標準にしない。別ツール・手書きSQL方式の案件へPrismaを持ち込まない。
- Prismaで`migrate dev`を採用する案件では、schema変更後、適用前にSQLを確認する場合は既存CLIの`migrate dev --name <変更名> --create-only`で草案を生成する。`--create-only`なしは生成した移行を含む未適用履歴のDB適用も行う。フラグ・設定方法は導入済みバージョンで確認し、CLIの取得・更新を無断で行わない。
- `--create-only`はオフライン生成やDB操作許可の省略ではない。開発DBとshadow DBの接続先・破棄可能性、履歴差分を確認し、生成時のDB操作も承認済みの隔離環境と期限付き能力に限定する。reset要求や予期しないdriftが出た場合は自動同意せず原因を報告する。
- 生成SQLのDROP、rename、NOT NULL、既存データ、制約・indexへの影響を確認する。データ移行、生成器が表現できない制約、データ保持のrename等は、未適用の生成物へ必要なSQLを補正する。SQL手書きが既存ツールの正規方式ならそれに従い、理由と検証方法を残す。
- 適用済み履歴を編集・削除して通さず、必要な修正は新規の前進マイグレーションにする。未承認のresetや`db push`へ置き換えない。環境・権限不足ならその操作だけを保留し、必要な許可・環境と代替案をPMへ返す。手動作成を承認回避の代わりにしない。
- 承認済みの隔離環境で必要な適用・既存データ保持・制約・回帰を検証し、reportへ生成／適用コマンド、手動補正理由、結果、未適用・未検証を区別して記録する。マイグレーションであるだけで追加のTL往復や独自承認工程を増やさない。

Prisma公式の[生成・適用コマンド](https://docs.prisma.io/docs/cli/migrate/dev)と[未適用SQLのカスタマイズ](https://docs.prisma.io/docs/orm/prisma-migrate/workflows/customizing-migrations)を参照できる。実際の操作はプロジェクトの導入済みバージョンに合わせる。

## 成功条件

- 指示書とspec.mdの受け入れ条件を満たしている。
- 番号付き受け入れ条件ごとに、実装箇所と検証証拠を説明できる。
- 必要な正常系・失敗系・境界値・副作用のテストがある。
- セキュリティ関連の変更では、認証・認可、入力検証、ログマスキングの該当項目をテストしている。
- 指定された検証がすべて成功している。
- 新規taskではreport.mdの`## 再現可能な検証コマンド`に、実行コマンドと結果を秘密値なしで記録している。
- 差分が承認済み範囲に収まり、既存規約・参照パターンと整合している。
- 実装担当による人間向け正式ドキュメントの変更がなく、必要な更新候補と確認済み事実をreport.mdへ記録している。
- 通知・外部送信がある場合、イベント、業務入口、受信者、チャネル、内容と機密性、認証・設定、重複抑止、失敗・再試行、検証方法が承認済みである。
- 未解決のセキュリティ懸念、既知の重大な不具合、無断のリファクタがない。
- policyで必須の場合は別コンテキストの内部検証担当が「合格」と判定し、その後に実装・テスト・設定を変更していない。低・標準リスクで省略する場合は具体的な根拠を記録する。
- 機械管理taskでは`flowctl validate`と`flowctl submit`が差分境界・成果物形式を合格としている。文書taskでは同じ受け入れ条件と証拠をPMへ提出する。

成功は「未コミット候補差分をPMへ提出可能」を意味する。コミット可、監査可能、監査合格、機能クローズのいずれも意味しない。

## 上限と停止条件

- 指示書に別指定がなければ、同じ未達条件への実装・検証の試行は最大5回とする。別の受け入れ条件へ進んだことだけを理由にタスク全体を停止しない。
- Builderと内部検証担当の往復も反復回数に含める。同じ原因・同じ内部検証指摘が3回続く、または変更しても進展がない場合は停止する。
- 仕様・指示書・既存実装が矛盾している、変更範囲の拡大が必要、受け入れ条件を検証できない場合は停止する。
- PM・Tech Lead判断の前提となった業務入口、呼出し元、既存挙動を実コードで確認できない、または確認結果が前提と食い違う場合は停止する。
- 通知・外部送信の対象イベント、受信者、チャネル、内容、重複抑止、失敗・再試行のいずれかが未確定なら停止する。
- サービス境界・アーキテクチャ・認証認可・秘密情報・個人情報・不可逆なデータ変更など、上流判断が必要になった場合は停止する。
- 破壊的操作、本番環境、共有DB、実credential、未承認の外部送信が必要な場合は実行せず停止する。
- 秘密情報の露出、権限逸脱、個人情報漏えいの疑いを見つけた場合は、値を表示・転記せず直ちに停止する。
- 必須の内部検証用サブエージェントを起動できない、または別コンテキストで実施できたか確認できない場合は停止する。親セッションによる代替確認で成功扱いにしない。

停止時は推測で作業を続けず、試した内容、最後の安全な状態、失敗の根拠、必要な判断を私へ報告する。PM・TL・正式監査を自分で起動しない。上流判断が必要でもTLへ直接渡さず、PMの独立セッションへ問題を戻すための貼り付け用プロンプトを提示する。

## 禁止事項

- テストの削除、skip化、アサーション弱体化、検証設定の緩和によって成功扱いにしない。
- 受け入れ条件、公開契約、エラー挙動を無断で変更しない。
- 指示範囲外の整理、命名変更、依存更新、リファクタを混ぜない。
- README、ガイド、運用手順、設計書、ADRなどの人間向け正式ドキュメントを変更しない。自動生成資料は指示書に正本とgeneratorが明記され、ガードの許可対象に含まれる場合だけ再生成する。文書運用で正式文書に分類される生成資料はPMへ返す。
- ループの途中・完了後ともgit変更操作やコミット依頼を行わない。変更ファイル一覧と推奨コミットメッセージはreport.mdへ記録し、PMの確認へ渡す。
- 環境変数や設定全体を一括表示せず、秘密情報をログや成果物へ残さない。
- 実credentialを使用せず、本番環境・共有DBを操作しない。
- 必須の内部検証の合格または低・標準リスクでの省略根拠を確認する前に、完了報告、summary.md、PM提出へ進まない。

現在の実装担当業務内では調査等にもサブエージェントを使ってよい。内部検証は高リスクまたはpolicyで必須の場合に行う。親セッションが全変更と検証結果に責任を持ち、サブエージェントにPM・TL・正式監査を代行させない。完了後はreport.md、summary.md、loop-state.mdのパスとPM用プロンプトだけを提示し、`$auditor`、`/auditor`、監査依頼文を出力しない。
