# 実装提出から監査までの固定ゲート

この手順は通常実装と監査是正の両方に適用する。指示書にこれと異なる工程順がある場合、勝手に選ばずPMが矛盾を解消してから進む。

## 固定する遷移

```text
実装担当が候補差分を完成
  → report.md / summary.md / loop-state.md をPMへ提出
  → PMが未コミット候補差分と証跡を裏取り
     ├─ 不備あり: 実装担当へ差し戻し
     └─ 実装候補可: PMが必要な正式ドキュメントを更新
  → PMがコード・テスト・仕様・正式ドキュメントを再照合
     ├─ 不整合あり: 実装担当へ差し戻し、PMの未確定文書変更は確定扱いにしない
     └─ コミット可: implementation-review.mdを作成
  → オーナーが承認済み候補差分をコミット
  → PMがコミット済み差分を再照合
  → PMがaudit-request.mdを作成
  → オーナーが独立監査セッションを開始
```

実装担当はコミットを依頼せず、PMセッションへの引き継ぎだけを行う。人間向け正式ドキュメントはPMが更新する。PMだけがコミット可否を判定し、コミット後の固定差分を確認して監査依頼を作成する。

## PMの実装提出ゲート

1. 指示書、spec.md、tasks.md、pre-summary.md（存在する場合）、report.md、summary.md、loop-state.mdを確認する。
2. このSkillの`scripts/validate_handoff.py`へtaskディレクトリを渡して実行する。終了コードが0でない場合は、その不足を含む実装担当向け差し戻し文を作成して停止する。
   実装担当の`flowctl submit`が`pm_review`へ遷移済みであることも`flowctl status`で確認する。
3. 指示書で実装前内部検証が必須、または実際の差分が認証・課金・不可逆なデータ変更・外部送信・別サービス契約・復旧不能になり得る並行状態遷移を含む場合、実装開始前の別コンテキスト検証が「実装開始可」であった証跡を確認する。開始後に作られた追認は認めない。
4. `git status --short`、追跡済み差分、未追跡ファイルを読み取り、指示範囲、禁止範囲、報告の変更ファイル一覧と一致するか確認する。秘密情報を含み得るファイル名を見つけた場合は内容を開かず停止する。
5. 実装担当がREADME、利用者ガイド、運用手順、設計書、ADRなどの人間向け正式ドキュメントを変更していないことを確認する。指示書に含まれていても例外にしない。自動生成資料は、指示書に正本と既存generatorが明記された場合だけ実装候補として認める。
6. 番号付き受け入れ条件、実装箇所、テスト、実行結果が対応するか確認する。とくに業務入口、全呼出し元、既存挙動、データ所有者、外部副作用が指示書の前提と一致するか実コードから再確認する。PMは安全なローカル検証を再実行して報告を裏取りしてよいが、実装や正式監査を代行しない。
7. 内部検証証跡が実際の別コンテキストのサブエージェント実行を示し、最終合格後に実装・テスト・設定・自動生成物が変わっていないことを確認する。曖昧な表現だけでは合格にしない。
8. 実装候補が仕様と一致した後、report.mdの「正式ドキュメント影響」を確認し、必要な正式ドキュメントをPM自身が更新する。アーキテクチャ、セキュリティ、データ設計、外部契約の記載は、対応するTech Lead判断がある場合だけ反映する。
9. PMの文書変更を含めてコード・テスト・specと再照合する。PMが変更できるのは人間向け正式ドキュメントだけであり、コード・テスト・設定・自動生成物の変更が必要なら実装担当へ戻す。PMによる正式ドキュメントだけの変更で実装担当の内部検証をやり直す必要はない。
10. 合格時はtaskディレクトリの`implementation-review.md`へ、base commit、確認時HEAD、実装担当が作成した候補ファイル、PMが変更した正式ドキュメント、各文書の根拠、PMが再実行した検証、未実行項目、残リスク、判定を分けて記録する。

不合格時は`flowctl pm-review --result return --summary <不足>`、合格時は`flowctl pm-review --result accept`を実行する。外部成果・パス・責務・リスク領域の拡大を伴う差し戻しだけ`--scope-change`を付け、オーナー再固定を必須にする。

この段階では`audit-request.md`を作成せず、監査用プロンプトも提示しない。次のアクションはオーナーによるコミットだけとする。

## コミット後の監査準備ゲート

オーナーからコミット完了とSHAを受け取った後、同じPMセッションで次を確認する。

1. ブランチとHEADが申告どおりで、HEADがbase commitから進んでいる。
2. `git diff <base>..<確定HEAD>`が空でなく、`implementation-review.md`で承認した候補差分と一致する。
3. タスク範囲の実装・テスト・設定・自動生成物・正式ドキュメントに未コミット変更が残っていない。既知の対象外差分がある場合は対象外として明記する。
4. report.md、summary.md、loop-state.mdとコミット済み差分の内容が矛盾していない。

すべて満たした場合だけ`audit-request.md`を作成する。監査依頼には作業ディレクトリ、base commit、確定HEAD、非空の監査範囲、実装・テスト・設定・自動生成物・PM更新済み正式ドキュメント、各文書の根拠となるspecとTech Lead判断、検証証跡、残リスクを記録する。その後にだけ、オーナーが開始するCodex監査・Claude監査用プロンプトを提示する。

オーナーのコミット後は`flowctl commit-recorded --head <SHA>`、audit-request.md完成後は`flowctl audit-ready`を実行する。両方が合格するまで監査文面を出さず、合格後も`flowctl next`が生成した貼り付け用プロンプトだけを使う。

## 自動差し戻し条件

次のいずれかがあれば、コミット可または監査可能と判定せず、オーナーへ判断を求めず実装担当向け差し戻し文を作成する。

- `report.md`、`summary.md`、`loop-state.md`の欠落または相互矛盾
- summary.mdの必須タグ欠落、規定外タグ、12行超過
- 必須の実装前内部検証がない、実装開始前に「実装開始可」になっていない、または前提確認が空欄・曖昧である
- 内部検証の実施方式、起動回数、起動記録、対象、条件別根拠、最終判定、修正票と対応、合格後変更有無の不足
- Builder自身の自己レビューを内部検証として扱っている
- 実装担当が人間向け正式ドキュメントを作成・編集・削除している、または正式ドキュメント影響の報告がない
- 業務入口・全呼出し元・既存挙動・データ所有者について、指示書の前提と実コードが一致しない、または確認根拠がない
- 外部送信のイベント、受信者、チャネル、内容と機密性、認証・設定、重複抑止、失敗・再試行、検証方法のいずれかが未確定なのに実装されている
- 報告と実際の変更ファイル、検証結果、対象範囲が一致しない
- コミット前の監査依頼、空の`git diff <base>..<確定HEAD>`、確定HEAD不明
- PM確認後または内部検証合格後に、再確認されていないプロダクト差分変更がある

形式検証スクリプトの合格は必要条件であり、仕様・差分・検証結果の裏取りを省略する根拠にはしない。
