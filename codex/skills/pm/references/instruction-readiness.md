# 実装指示書の準備ゲート

実装指示書は、実装担当の仮説を承認済み事実へ変換する場所ではない。PMは次を満たすまで`instruction.md`を発行しない。

最初に`docs/flow/<機能名>/scope-baseline.md`を作り、各要求を`| 要求ID | 承認済みの外部成果 | 変更可能パス | 許可するリスク領域 | リスク区分 | 変更上限 |`の表へ一行で記載する。変更可能パスにはコード・テスト・設定・migration・PMが更新する正式ドキュメントを含める。リスク区分は`低・標準・高`、変更上限は`20ファイル / 2000行`形式とし、`## 明示的な対象外`も置く。オーナーが`flowctl scope-lock`で固定するまでtaskを初期化しない。指示書は固定済み要求を一件だけ参照し、外部成果の文を変更・結合しない。

## 事実と判断の根拠

実装対象となる挙動ごとに、少なくとも次を実コード、既存テスト、決定済み資料から確認する。

| 確認項目 | 必要な根拠 |
| --- | --- |
| 利用者要求 | オーナーの決定、承認済みspec、既存の正式仕様 |
| 業務入口 | 実際のroute、service、job、eventと全呼出し元 |
| 既存挙動 | 現在の分岐、状態変更、データ更新、外部副作用 |
| 変更責務 | 変更を所有するcomponentと、変更してはならない境界 |
| 検証方法 | 外部から観測できる期待結果と、それを保証するテスト |

実装担当の`pre-summary.md`、過去の提案、PMの推奨案は、それ自体を事実の根拠にしない。特に課金・plan・entitlement、登録・認証、削除、通知、外部送信では、処理名だけで業務意味を推定せず、呼出し元と利用者経路を確認する。確認できないものは未決事項としてオーナーへ戻す。

PMまたはオーナーは「誰に、いつ、何を起こすか」というプロダクト・業務判断を確定する。Tech Leadは、確定した業務要件に対する技術方式と安全性を判断する。業務入口、課金結果、通知対象などが未確定のままTech Leadへ方式決定を依頼しない。

## 通知・外部送信の完全性

通知、Webhook、メール、チャット、ログ転送など新しい外部副作用を実装対象にする場合、指示書へ次をすべて固定する。

- 対象イベントと発火する業務入口
- 受信者・対象利用者
- チャネルまたは送信先
- 送信内容と、秘密情報・個人情報を含めないための分類
- 認証・認可と設定の所有者
- 重複抑止・冪等性
- timeout、再試行、送信失敗、部分成功時の扱い
- 監視・監査・テストで確認する結果

一つでも未確定なら、その副作用を今回の対象外にするか、オーナーへ判断を求める。「高優先度で通知する」など抽象的な文だけで、特定チャネルの実装を許可しない。保存・送信経路や機密性の技術判断が残る場合だけTech Leadへ相談する。

## タスク境界

一つのタスクは、原則として一つの主要な外部挙動と一つの不可逆境界に限定する。次の独立したリスク領域を、単に同じ機能であるという理由だけで一つの指示書へまとめない。

- 認証・認可・テナント境界
- 課金・plan・entitlement
- schema・migration・不可逆なデータ変更
- 外部通知・外部送信
- 外部サービス契約・別リポジトリ
- 並行実行・二重実行・復旧不能になり得る状態遷移

原子性などの理由で分割できない場合は、分割不能の根拠、許可する領域・ファイル、領域ごとの確認点、停止条件を`tasks.md`と`instruction.md`へ記載する。実装中に新しいリスク領域が必要になった場合は、指示書を拡張せずPMへ戻す。

実装中に見つかり得る不足は事前に次で区別する。元の外部成果がその変更なしでは成立せず、固定済みパス・リスク内で新しい利用者成果や責務を増やさない内部処理・エラー処理・直接テストは同じタスクに含められる。「あると良い」改善、将来対応、新しい通知・課金・業務入口・別サービス責務などは別候補にする。判断根拠がないものは実装担当に委ねない。

## 実装前内部検証

指示書には次のどちらかを独立した1行でそのまま記載し、次の行に`実装前内部検証の理由:`を書く。

- `実装前内部検証: 必須`
- `実装前内部検証: 不要`

上記リスク領域を含む場合、複数の業務入口へ影響する場合、または分割不能な複合タスクでは必須とする。実装担当は`pre-summary.md`作成後、プロダクトコードを変更する前に別コンテキストの内部検証担当を起動し、事実根拠、呼出し元、指示の完全性、範囲を確認する。

## 正式ドキュメント

指示書には更新が必要になり得る正式ドキュメントを「PM更新候補」として記載し、実装担当の変更対象へ含めない。自動生成物は、正本と既存generatorを明示した場合だけ実装対象にできる。

## 発行条件

次をすべて満たす場合だけ実装指示書を発行する。

- 受け入れ条件が、確認済み事実とオーナーの決定に基づいている
- 業務入口と呼出し元を確認している
- 外部副作用が一意に実装できるか、明示的に対象外である
- タスク境界が過大でないか、分割不能の根拠がある
- Tech Lead判断とプロダクト判断を混同していない
- 正式ドキュメントが実装担当の変更範囲に含まれていない
- `リスク区分`、`主要要求ID`、`主要な外部挙動数: 1`、固定済み文と同一の`主要な外部挙動`、`不可逆境界数: 0|1`、`不可逆境界`、`リスク領域`が各一行で記載されている
- `## 実装担当の変更許可パス`が固定済み最大パス内で、受け入れ条件が`受け入れ条件 / 外部から観測できる期待結果 / 検証方法`の3列表になっている
- `flowctl instruction-ready`が合格している
