# 実装指示書の準備

目的は、実装担当が既存資料を利用して変更と検証に入れること。ユーザーの依頼に必要な仕様と境界を確定し、実装の詳細調査は担当へ渡す。

## 根拠を使う

ユーザーの確定事項、現行spec、関連TL決定、最新監査と報告を使う。資料の根拠が現在のコード・対象SHAに適用できるかを要所で照合する。矛盾がなければ過去の設計判断をやり直さない。未確認の提案は確定仕様へ昇格させない。

調べるのは、主要な入口、既存パターン、変更責務、重要な失敗・認可・不可逆境界。通常の内部関数や全repoをPMが網羅調査しない。新機能では必要な調査が増え得るが、判断論点と関係する資料を明確にする。

## 必要な内容

- 目的、依頼・決定の根拠、対象外、リスク
- 対象repo、ブランチと比較基準、既存差分の扱い
- 現行spec／監査等へのリンクと必要な決定
- 受け入れ条件ごとの期待結果・検証方法
- 実装担当の変更許可パス、既存パターンの参照先
- 必要時の停止条件、PM更新の正式文書候補
- マイグレーションがある場合は既存ツールでの生成方針と検証対象。生成時のDB操作と適用を区別し、接続・適用の許可は既存の安全境界に従う。通常の生成手順だけで追加TL承認を設けない

文書中心の運用ではこれを簡潔に記す。変更パスのガードだけは次の形式を使う。本文の仕様・期待結果は自然な文章でよく、定型表へ全面変換しない。

```markdown
## 実装担当の変更許可パス

- `src/profile/**`
- `tests/profile/**`
```

例のパスをそのまま使わず、そのプロジェクトの既存配置に合わせる。コード・試験は責務単位の狭いglob、認証境界・設定・依存・migrationは具体的な対象を示す。README等の正式文書や全repoの`**`を許可しない。PM作成のinstruction.mdから既存名の指示書を参照してもよい。

小さな不具合や是正の依頼は、現在の指示書と既存仕様で十分ならspec・スコープ・taskを作り直さない。受け入れ条件に不可欠な範囲内の不足は同じtaskへ含める。将来用の機能、通知、課金、別サービス責務は関連だけで追加しない。

## 未決事項の扱い

業務上の「誰に、いつ、何が起きるか」はPMとオーナーの判断。新しい通知・外部送信はイベント、受信者、経路、内容・機密性、重複・失敗時の扱いを確定する。既存挙動を保持する修正では既存契約を参照できる。

技術方式の未決が認可・秘密情報・不可逆性等の重大リスクへ影響するときだけTLへ相談する。通常の実装方式や、承認済み方式への適合修正をTL承認へ変換しない。依存関係のない指摘は判断待ち項目と分けて指示できるが、未決の危険な部分を実装可としない。

ユーザーが途中で不足を採用した場合、今回の目的・責務・リスク内か確認し指示書へ反映する。明示された完了条件は、速度の要望だけで変えない。

## 機械管理を使っているtask

既存のpolicyとscope-lockを維持する。`scope-check`は必要な固定の前にPMが実行する。許可範囲内の具体化では再固定しない。既存の許可パスを本当に増やす場合だけ、差分と理由を示して再承認する。

新規に機械管理を選ぶ場合は、scope-baselineの要求・範囲・リスク・上限・オーナー承認サマリを固定後、initしinstruction-readyを通す。機械管理用の必須フィールドは既存のparse_instruction検査に従う。未初期化資料のキャッチアップや是正案作成にこの登録を強制しない。

指示の更新で実装中コードと食い違うときは停止・引き継ぎを確認する。固定された承認や監査構成を無断で変えず、文書上の進捗を機械状態の成功へ置き換えない。
